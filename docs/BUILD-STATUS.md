**Backup/restore drill.** Recognisable data (3 accounts, 2 campaigns, 14 chat lines incl. a whisper, 2 handouts with an uploaded PNG, a scheduled session with an RSVP, a profile edit, two settings) -> `backup.sh` (12 KB database, 2 KB media; a drill with `--audio` also) -> `down -v` of the project -> a **new bundle directory with no `.env`** -> `restore.sh <folder> --yes --with-config` (23 s) -> row counts identical, passwords sign in, history and whisper present, handout bytes identical (sha256), RSVP and settings back. **Findings for the backend owner (not fixed here):** (1) a restart during a recording marks it `failed` ("interrupted by a restart"; 0 tracks): the DM must start a new one, and the players' timer
ends; documented behaviour should say so. (2) No SIGTERM handler (worked around in Compose). (3) The 3 in-flight lines above: the server assigns the id, so a retry after a reconnect cannot be deduplicated server-side (SYNC-PROTOCOL says the client-generated `id` dedupes retried sends; the hub uses a fresh UUID).
Disk used by the rehearsal: about 80 MB of unique image layers (the published backend image; the rest was already present) plus about 100 MB of scratch files, all in the session's scratch directory; volumes removed with `down -v`.

## Stage 4 additions (2026-11-08)

- **Idle cost, measured:** the debug build hidden in the tray (no window open) used **0.07% CPU over 30 s** and ~94 MB RSS. The release build and a 4-hour run are not measured — `tauri-client/scripts/soak.sh` records CPU/RSS per minute for that.
- **Crash recovery:** `src-tauri/src/supervisor.rs`. Release builds (or `VTT_SUPERVISE=1`) run a supervisor that restarts the app after an abnormal exit; verified live by SIGKILLing the child (restarted in 1 s). `VTT_NO_SUPERVISE=1` opts out. A clean exit (tray Quit) ends both. Not verified: a real native crash (SIGSEGV from the shell was swallowed by the process's own handlers), or the Quit path through the tray.
- **Links and autostart:** `vtt-chat://connect?server=…` registers on Linux at start (`~/.local/share/applications/vtt-chat-app-handler.desktop`); firing one at the running app kept a single instance. Installed builds on Windows/macOS register the scheme through the bundle (no installer is built yet). Autostart is a Settings toggle, off by default; verified only by compiling and the plugin's own behaviour, not by logging out and in.
- **Hardened:** server addresses are now validated as `host[:port]` (`javascript:alert(1)` used to be accepted as a host).
- **Connection screen:** `LinkProbe` reads WebRTC's remote-inbound report (RTT, jitter, loss); unit-tested on constructed stats, **not yet seen against a real LiveKit server** (none is installed on the dev box).
- **Open decision — auto-update:** needs (1) a signing key pair (the private key must be kept secret and backed up) and (2) somewhere that serves `latest.json` plus the installers. For a self-hosted project the natural place is the operator's own backend (`CLIENT_URL_*`), but then the _server_ decides which client binary players run. Not built until chosen.
