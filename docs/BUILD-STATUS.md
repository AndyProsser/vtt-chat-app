## AI summary pipeline reliability (interim), 2026-11-26

**Built and unit-tested**, following
[docs/superpowers/plans/2026-11-26-ai-pipeline-reliability-interim-fix.md](../docs/superpowers/plans/2026-11-26-ai-pipeline-reliability-interim-fix.md)
(design: [docs/superpowers/specs/2026-11-26-ai-pipeline-reliability-design.md](../docs/superpowers/specs/2026-11-26-ai-pipeline-reliability-design.md)).
Found while running a real GPU-vs-CPU timing comparison: the job died with "fetch failed" at
almost exactly the one-hour mark, three times across its retries. Root cause was a hardcoded
60-minute request timeout (`longFetch.ts`) — the only timeout a local Ollama call actually had —
tripping on a chunk that genuinely couldn't finish on CPU in time, plus a remote "token repeat
limit" abort being classified identically to the server being unreachable, silently triggering
the same permanent fallback-to-local a real outage would.

**Revised the same day, after review and a follow-up conversation with Andy:** the first build
gated local-CPU LLM fallback on the recording's duration (`ai.fallback.max-local-minutes`,
default 20 minutes). Review correctly flagged that this effectively disabled fallback for any real
session (3–5 hours), contradicting CLAUDE.md §5's "never lost" promise. Andy's call: uphold it —
a job should never be refused for being long, and should run as long as it genuinely takes
("I just want this to complete even if it takes 8+ hours… no one cares because they are
sleeping"). `ai.fallback.max-local-minutes` now defaults to **no limit** (`null`) and stays only
as an _opt-in_ cap for an operator who deliberately wants the opposite (0 = never fall back to
local, a number = that many minutes). What actually protects against the original bug — a job
grinding for nothing — is the repeat-limit classification and retry-once-then-fail (below), plus
a per-call liveness bound, not a guess about total duration: those catch a call that's genuinely
_stuck_, and a merely _slow_ one is allowed to keep going, call after call, for as long as it
takes. A local generate call's own timeout (`LOCAL_GENERATE_TIMEOUT_MS`) is **45 minutes** (raised
from an initial 20 during review — on the project's own no-AVX test VM, measured elsewhere
([RECORDING-AND-SUMMARIES.md](RECORDING-AND-SUMMARIES.md), "Sampling": 3.2 read / 1.8 write
tokens/s, versus roughly 50–100/8–12 on a modern CPU), a single 6,000-char chunk is itself close
to 20 minutes, which left too little margin for a bound meant to catch only a genuinely hung call,
not a slow one). This is deliberately a liveness check, not a size gate: if a call times out, that
one attempt fails, and the job resumes from its already-completed chapters on retry (existing
machinery, unchanged) — a stuck call costs one attempt, never the whole recording.

The default note-taking chunk size (`DEFAULT_CHUNK_CHARS`) is halved, 12,000 → 6,000 characters,
to bound a single call's worst-case generation time further. A repeat-limit abort is retried once
on the same backend before the job fails with a message that names it plainly, rather than a
generic "fetch failed"/"unreachable". The scribe's note-taking prompt was also tightened to
prioritise consequential events over exhaustive completeness — a deliberate, flagged relaxation of
the scribe's own completeness instruction (not of Stage 12 D's "decision 7," the unreadable-notes
retry ladder, which this leaves untouched), scoped to this release and meant to be revisited once
the Campaign Graph (0.7+) exists.

**Explicitly out of scope** (interim fix, not the real solution): the Campaign Graph itself; real
mid-call progress-watching (streaming tokens from Ollama and extending a live call rather than
waiting for the whole response) — Andy asked about this directly; it's a real 0.7+ possibility,
not built here, because it needs switching every local/remote generate call from `stream: false`
to `stream: true`, a bigger architectural change than this fix's bounded-timeout-plus-resumable-
retry approach, which delivers the same practical outcome (slow jobs finish, stuck ones don't
block forever) without it; automatic re-chunking when a repeat-limit abort recurs ("job
optimisation"); cross-chapter LLM concurrency.

**Verified:** `npm test -w shared && npm test -w ai && npm test -w backend`, `npm run lint`,
`npm run format:check` and `npm run typecheck` all clean. **Not yet verified:** a real local-only
run against the actual recording that triggered this, to see how many hours it genuinely takes
end to end and whether 45 minutes gives real chunks enough margin on that hardware.

**Real-world retest, 2026-11-27: the "fetch failed" recording, re-run against the fix.** Found the
retry resumed only once every chapter had already succeeded, not from a mid-batch failure — the
claim above ("the job resumes from its already-completed chapters on retry") was true for a later
phase failing after notes were fully stored, not for note-taking itself dying partway through a
many-chapter recording, which is exactly what this recording did on every attempt. Fixed: each
chapter's notes are now cached as soon as they're taken (`chapter_notes_cache`, a table separate
from `summaries` so a half-finished chapter is never visible through the records API), and a retry
checks it before calling the scribe again. Also traced the repeat-limit abort itself to its real
cause by replaying the failing content directly against the remote Ollama server, outside the job:
not the model's weights (a re-pull "fixed" it only by coincidence — deleting a model forces an
unload), not the content (a trivial one-line prompt failed too, once the server had been under
load for a while), not `repeat_penalty` or disabling "thinking" (both tested, no effect). It is the
server's loaded GPU/runtime state degrading under sustained serving until every call aborts,
confirmed by forcing an unload+reload (`keep_alive: 0`) and watching the exact same failing
prompt succeed immediately after — then degrade again within that one job's own call volume.
Swapping to a smaller model (`qwen3.5:4b`) on the same server showed the same degradation, ruling
out model size. That part is an operator-side Ollama/GPU issue, not something this code can fix;
`docs/guides/OPERATOR-GUIDE.md` §11 has the diagnosis and the reload workaround.

**Resolution, same day: the recording completed end to end for the first time.** The per-chapter
cache meant each retry only had to redo the one chapter still failing, narrowing the problem down
chapter by chapter instead of restarting from scratch; direct, repeated testing against the
content showed the abort was genuinely probabilistic, not a deterministic trigger from that
chapter's content. Andy then updated Ollama (0.40.17 → 0.40.18, a llama.cpp bump), set
`OLLAMA_NUM_PARALLEL=1` (serializing requests — concurrent chapters had shared the GPU earlier in
this same investigation), dropped the quantized `OLLAMA_KV_CACHE_TYPE=q8_0` for the full-precision
default, and raised `OLLAMA_CONTEXT_LENGTH` 12288 → 16384; `ai.llm.context` was raised to match.
After an Ollama restart with that config, the stubborn chapter succeeded and the whole job
completed: 10 chapter summaries, 5 character tales, the DM brief, the combined notes and the
session tale, all written. Which of those changes actually mattered isn't isolated — they were
applied together under time pressure — but `OLLAMA_NUM_PARALLEL=1` is the best-supported one,
matching the concurrent-GPU-load pattern observed earlier. **A real local-only (CPU fallback) run
of this recording is still not verified** — only the remote GPU path has now completed cleanly.

**Also found and fixed the same day:** a character's tale shared a chapter's word cap (~175 words);
reading `ministral-3:8b`'s tales back (the model now in use, chosen after this same investigation)
they ran to roughly double that. Character tales now have their own, smaller cap (100/150/200
across short/default/long) instead of deriving from the session's.

## Adaptive audio-pipeline concurrency, 2026-11-26

**Built and unit-tested**, following
[docs/superpowers/plans/2026-11-26-adaptive-audio-pipeline-concurrency.md](../docs/superpowers/plans/2026-11-26-adaptive-audio-pipeline-concurrency.md)
(design: [docs/superpowers/specs/2026-11-26-adaptive-audio-pipeline-concurrency-design.md](../docs/superpowers/specs/2026-11-26-adaptive-audio-pipeline-concurrency-design.md)).
Found while checking a real session's processing time on the VM: tracks transcribed one at a time,
and within a track, windows one at a time — Whisper spends most of its time waiting on the next
sliced clip, not transcribing. `processRecording.ts`'s track loop now dispatches several tracks at
once through a small concurrency pool (`dynamicPool.ts`), with a shared mutex keeping Whisper
itself at one request in flight regardless of how many tracks run concurrently. How many tracks run
at once comes from a new activity governor (`activityGovernor.ts`): a disposable mirror of the
backend's online-user count (new `instance_runtime` table, written by `hub.ts` on every
connect/disconnect) drives it first — nobody online uses up to the host's core count, anyone online
drops to a conservative default (`ai.processing.active-concurrency`, 2) — and CPU load
(`ai.processing.cpu-threshold-percent`, 70%) is a backup clamp to 1, consulted only once presence
says someone's there. An unreadable presence signal fails toward "someone's online," the opposite
of `quietGate`'s own fail-open convention, since here the wrong default is the one that would
contend with a real player. `quietGate`'s existing hard pause (`ai.pause-while-recording`) now also
covers this track dispatch, closing a gap where parallel clip-prep would otherwise have run even
while a table recorded elsewhere.

**Explicitly out of scope** (Andy, during planning): cross-recording concurrency — the worker still
processes exactly one job (one recording) at a time, tables strictly in order; multiple concurrent
Whisper requests — the bottleneck identified was clip preparation, not Whisper's own throughput.

**Verified:** `npm run lint && npm run build && npm run typecheck && npm test && npm run format:check`
all clean across the whole repo. **Not yet verified:** a real multi-track reprocess on the dev VM
actually overlapping tracks in the worker log (the plan's own "Done when" calls for a manual
spot-check before trusting this in practice); the Postgres-backed `onlineUserCount` test runs only
in skipped form in every environment used so far (no `TEST_DATABASE_URL` set).

## AI context-window tuning via `vtt-admin status`, 2026-11-24

**Built, on branch `worktree-ai-context-tuning`, following
[docs/superpowers/plans/2026-11-24-ai-context-tuning.md](../docs/superpowers/plans/2026-11-24-ai-context-tuning.md):**
closes two of the chunking work's own gaps (below) and gives the operator a way to check and fix a
context-window mismatch instead of guessing. `vtt-admin status` gains an AI section: for `local`/`remote` it
grades what the worker finds asking Ollama directly (`/api/ps` for what's actually being served,
`/api/show` for the model's trained maximum) against what the app assumes; for Claude, a built-in per-model
table (`ai/consts/claude.ts`) now drives the real window directly, no setting involved. Assuming _more_ than
the backend can serve fails the check — a real truncation risk, not a formality; assuming _less_ (unused
headroom) is a warning with a hint. `vtt-admin status --tune` applies whatever was found. Along the way,
`local`'s own fixed `num_ctx` (hardcoded 8,192 in the worker) was replaced with the configured
`ai.llm.context`, read fresh on every call — `local` had never actually been tunable before this.

**Known limits:** the worker checks periodically, independent of job processing (never on the job's own hot
path), so `status` can be a few minutes stale after a config change; `--tune` acts on that last-checked
value, not a fresh on-demand query. The bigger `vtt-admin test ai|voice|full` idea and external
connectivity checking were both parked (ROADMAP.md, Future ideas) rather than built now.

## Stage 9, 2026-11-16: idle CPU and the one-shot containers (branch `stage-9-hardening`, 0.5.2)

**Built and checked on the dev PC** (local images, the `vtt-smoke` stack with the GPU override, and a throwaway project with new
volumes and tiny models):

- **Idle CPU.** Measured on the real VM first (read-only): about half a core, nearly all of it Docker health-check commands and
  the daemon launching them ([the table](architecture/DEPLOYMENT-AND-TRANSPORT.md#start-up-and-idle-cost)). After the change,
  on the dev PC: 43 → 6 health-check commands a minute; containers 5.7% → 2.4% of a core.
  **On the VM (2026-11-16, `0.5.1-dev.2` installed with the installer as an update):** containers 26.7% → 6.4% of a core, the
  whole machine 52.8% → 34 to 37%. The Docker daemon's own 27% did not move: a profile shows it is a host monitoring agent
  listing and inspecting 52 images every 30 s, not the health checks (same link).
- **No one-shot containers.** A fresh stack (`postgres valkey backend worker whisper ollama`) was healthy in 6 s; the Whisper
  model and the summary model then downloaded in the background and `vtt-admin status` printed `local AI   summary model ready,
Whisper ready`. New volumes came up owned by uid 1000 (media) and 1001 (recordings); a file written as Egress's user was
  deleted by the worker. With model names that do not exist the stack still started, `vtt-admin status` printed `FAIL local AI`
  with the reason, `/api/status` reported `summary model` down, and a `docker stop` of the retrying Whisper container returned at once.

**Backup/restore drill.** Recognisable data (3 accounts, 2 campaigns, 14 chat lines incl. a whisper, 2 handouts with an uploaded PNG, a scheduled session with an RSVP, a profile edit, two settings) -> `backup.sh` (12 KB database, 2 KB media; a drill with `--audio` also) -> `down -v` of the project -> a **new bundle directory with no `.env`** -> `restore.sh <folder> --yes --with-config` (23 s) -> row counts identical, passwords sign in, history and whisper present, handout bytes identical (sha256), RSVP and settings back. In-place restore: a session from before the backup still works, one made after is signed out, post-backup chat gone, replay buffer cleared, `--audio` files replaced (planted file removed, backed-up file restored byte for byte). Notes: with `localhost` Caddy generates a new CA on a new machine (re-trust it; its volume is not backed up); not tested with large real recordings.

(919 whispers, 624 quick-command RSVPs), presence and voice-state frames, 505 deliberate disconnect/reconnects (each client about once a minute), two recording

**Findings for the backend owner (not fixed here):** (1) a restart during a recording marks it `failed` ("interrupted by a restart"; 0 tracks): the DM must start a new one, and the players' timer

(3) The 3 in-flight lines above: the server assigns the id, so a retry after a reconnect cannot be deduplicated server-side (SYNC-PROTOCOL says the client-generated `id` dedupes retried sends; the hub uses a fresh UUID).

## Stage 4 additions (2026-11-08)

- **Idle cost, measured:** the debug build hidden in the tray (no window open) used **0.07% CPU over 30 s** and ~94 MB RSS. The release build and a 4-hour run are not measured — `tauri-client/scripts/soak.sh` records CPU/RSS per minute for that.
- **Crash recovery:** `src-tauri/src/supervisor.rs`. Release builds (or `VTT_SUPERVISE=1`) run a supervisor that restarts the app after an abnormal exit; verified live by SIGKILLing the child (restarted in 1 s). `VTT_NO_SUPERVISE=1` opts out. A clean exit (tray Quit) ends both. Not verified: a real native crash (SIGSEGV from the shell was swallowed by the process's own handlers), or the Quit path through the tray.
- **Links and autostart:** `vtt-chat://connect?server=…` registers on Linux at start (`~/.local/share/applications/vtt-chat-app-handler.desktop`); firing one at the running app kept a single instance. Installed builds on Windows/macOS register the scheme through the bundle (no installer is built yet). Autostart is a Settings toggle, off by default; verified only by compiling and the plugin's own behaviour, not by logging out and in.
- **Hardened:** server addresses are now validated as `host[:port]` (`javascript:alert(1)` used to be accepted as a host).
- **Connection screen:** `LinkProbe` reads WebRTC's remote-inbound report (RTT, jitter, loss); unit-tested on constructed stats, **not yet seen against a real LiveKit server** (none is installed on the dev box).
- **Open decision — auto-update:** needs (1) a signing key pair (the private key must be kept secret and backed up) and (2) somewhere that serves `latest.json` plus the installers. For a self-hosted project the natural place is the operator's own backend (`CLIENT_URL_*`), but then the _server_ decides which client binary players run. Not built until chosen.
